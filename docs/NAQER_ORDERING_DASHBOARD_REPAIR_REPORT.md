## 1. السبب الجذري لخطأ معاينة الطلب (Root Cause of Runtime Error & Digest 3624372193)

### التشخيص والتحليل الدقيق
عند النقر على معاينة الطلب أو الانتقال لتفاصيل الطلب في لوحة التحكم كان يظهر للمستخدم:
`حدث خطأ غير متوقع — مرجع الخطأ: 3624372193`

باستخراج سجلات خادم التطبيق وتتبع الـ Digest `3624372193`، تبيّن الآتي:
```
Error: Event handlers cannot be passed to Client Component props.
  <button type="button" className=... onClick={function onClick} style=... children=...>
                                              ^^^^^^^^^^^^^^^^^^
If you need interactivity, consider converting part of this to a Client Component.
  digest: '3624372193'
```

### السبب الفني المباشر
- في الصفحة `app/admin/(shell)/orders/[id]/page.tsx`، وهي **React Server Component** (`async function AdminOrderDetailPage` بدون دالة عميل `'use client'`)، كان هناك زر طباعة تجريبي يحمل المعالج:
  ```tsx
  <button type="button" onClick={() => {}}>طباعة</button>
  ```
- في بنية React Server Components في Next.js، يُحظر تماماً تمرير دوال أو معالجات أحداث (`onClick` / `onChange`) إلى عناصر الـ DOM مباشرة داخل الـ Server Component.
- عند محاولة تتبع أو عرض أي طلب، كان هذا السطر يُفجر استثناء فوري أثناء الـ SSR، ويتم التقاطه في معالج الأخطاء `app/admin/error.tsx` الذي يعرض للمستخدم رسالة الخطأ ورقم الـ Digest.

### المعالجة الجذرية
1. تم استئصال معالج الـ `onClick` غير الصالح من مكون الخادم في `app/admin/(shell)/orders/[id]/page.tsx`.
2. تم فحص كامل ملفات المشروع بمسح مؤتمت (`scratch/check-onclick.cjs`) والتأكد من عدم وجود أي معالج أحداث في أي Server Component آخر في المشروع.
3. تم التحقق من سلامة دورة الطلب بالكامل (`Cart -> CheckoutModal -> Branch -> Order Type -> Details -> Payment -> API -> WhatsApp -> Receipt`).

## 2. توحيد مصدر بيانات المنيو والداشبورد (Unified Data Source Architecture)

### مراجعة مصادر البيانات قبل التوحيد (Before Audit)
- **المنيو العام (`/ar`, `/en`):** كان يقرأ من `lib/backup-menu-db.ts` المعتمد على النسخة الاحتياطية الموثقة `backups/backup-naqer-verified.json` ويعرض 151 منتجاً و18 قسماً.
- **لوحة التحكم (`/admin/dashboard`, `/admin/products`, `/admin/categories`):** كانت تستدعي عميل `prisma` المرتبط بقاعدة البيانات التجريبية/Staging أو تعود ببيانات ناقصة (42 منتجاً فقط) ومعرفات مختلفة، مما خلق فجوة تامة وعدم تطابق بين ما يراه العميل وما تراه الإدارة.

### بنية التوحيد المطبقة (After - Unified Data Engine)
تم بناء محرك بيانات محلي متطور وذري `lib/local-db-engine.ts` مع ربطه كطبقة وصول موحدة (Unified Data Access Layer):
1. **المصدر التأسيسي:** النسخة الاحتياطية الموثقة `backups/backup-naqer-verified.json` تحتوي على 151 منتجاً أصلياً، 18 قسماً، 27 قطاعاً، 167 سعراً/متغيراً، 151 صورة، وفرعين وإعدادات المطعم.
2. **طبقة التعديل المعزولة (Atomic Overlay):** تم إنشاء مخزن ذري `data/local-db-overlay.json` يقوم بحفظ وتتبع أي تعديل محلي (تعديل منتج، إخفاء، تغيير أسعار، أو إضافة أقسام) دون المساس بملف النسخة الاحتياطية الأصلي نهائياً.
3. **تفويض عميل Prisma (Prisma Delegation):** تم تعديل `lib/prisma.ts` ليعمل كـ Proxy شفاف في الوضع المحلي؛ بحيث توجه جميع استعلامات `prisma.product.*`, `prisma.category.*`, `prisma.branch.*`, `prisma.restaurantSettings.*` تلقائياً إلى محرك البيانات الموحد.
4. **تزامن المنيو العام والداشبورد:** تم تحديث `lib/backup-menu-db.ts` ليقرأ مباشرة من نفس محرك البيانات الموحد. وبذلك، أي تعديل يجريه الأدمن من الداشبورد (مثل إخفاء منتج أو تعديل اسمه) ينعكس **فورياً** في المنيو العام، ويستمر محفوظاً بعد إعادة تشغيل الخادم.

### نتائج اختبارات التطابق
- **الأقسام:** 18 قسماً متطابقة بالمعرفات والأسماء في المنيو والداشبورد.
- **المنتجات:** 151 منتجاً متطابقة بكامل تفاصيلها وأسعارها وصورها.
- **الفروع:** الفرعان الأصليان (`فرع جمصة` و`فرع دمياط الجديدة`).
- **الصور والمتغيرات:** 167 متغيراً و151 صورة متطابقة تماماً.

## 3. صفحة إعدادات وتفعيل الطلبات (`/admin/order-settings`)

تمت إضافة صفحة تحكم متكاملة مخصصة لمدير النظام فقط (`OWNER` / `ADMIN`) لإدارة استقبال الطلبات:
- **المسار:** [http://127.0.0.1:3000/admin/order-settings](http://127.0.0.1:3000/admin/order-settings)

### الميزات والإعدادات المتاحة
1. **التحكم العام بالمنيو:**
   - وضع استقبال الطلبات مفعّل (`VIEW_AND_ORDER`).
   - وضع العرض وتصفح المنيو فقط (`VIEW_ONLY`).
   - وضع الإغلاق المؤقت للمطعم (`TEMPORARILY_CLOSED`).
   - تحرير رسالة الإغلاق المخصصة باللغتين العربية والإنجليزية.
2. **التحكم في أنواع الطلبات:**
   - تفعيل/تعطيل التوصيل للمنزل (`allowDelivery`).
   - تفعيل/تعطيل الاستلام من الفرع (`allowTakeaway`).
3. **التحكم التفصيلي على مستوى كل فرع:**
   - فتح / إغلاق الفرع (`isOpen`).
   - استقبال الطلبات في الفرع (`isOrderable`).
   - تخصيص أنواع الطلبات لكل فرع على حدة.
   - تحديد أيام ومواعيد العمل.
   - رسالة مخصصة لكل فرع عند الإغلاق أو الصيانة.
4. **الحماية والإنفاذ من جانب الخادم (Server Enforcement):**
   - تم ربط الـ API `/api/checkout` للتحقق الصارم من حالة النظام وحالة الفرع ونوع الطلب قبل إنشاء أي طلب، مع إرجاع رسائل خطأ واضحة بالعربية والإنجليزية عند التوقف.
   - موظف الطلبات (`ORDERS_STAFF`) محظور تماماً من فتح هذه الصفحة أو استدعاء الـ API الخاص بها (`403 Forbidden`).

## 4. تطوير واجهة إدارة الطلبات بمستوى Premium SaaS (`/admin/orders`)

تمت إعادة تصميم شاشة الطلبات لتتوافق تماماً مع نظام التصميم الراقي للداشبورد:

### أ. شريط المؤشرات والإحصائيات الحية (6 بطاقات بيانات حقيقية):
1. **إجمالي الطلبات:** العدد الكلي للعمليات المسجلة في النظام.
2. **طلبات جديدة:** الطلبات التي بانتظار مراجعة وقبول الإدارة (`PENDING_WHATSAPP`, `CUSTOMER_CONFIRMED_SENT`, `RECEIVED`).
3. **قيد التنفيذ والتحضير:** الطلبات المعتمدة والتي يتم طهيها أو تسليمها (`CONFIRMED`, `PREPARING`, `READY`, `OUT_FOR_DELIVERY`).
4. **طلبات مكتملة:** الطلبات التي سُلمت للعملاء بنجاح (`COMPLETED`).
5. **مرفوضة / ملغاة:** الطلبات المعتذر عنها أو المنتهية (`REJECTED`, `CANCELLED`, `EXPIRED`).
6. **مبيعات معتمدة:** إجمالي الإيرادات المالية المحسوبة **فقط** من الطلبات المعتمدة والمكتملة (تم استبعاد الطلبات المعلقة أو المرفوضة أو الملغاة تماماً من الإيرادات).

### ب. شريط البحث والتصفية المتقدم:
- بحث فوري برقم الطلب، كود التحقق، رقم الهاتف، أو اسم العميل.
- فلترة متعددة حسب الحالة التشغيلية.
- فلترة حسب الفرع وحسب نوع الطلب (توصيل / استلام).
- فلترة حسب التاريخ (اليوم، أمس، آخر 7 أيام، هذا الشهر، الكل).
- ترتيب متقدم (الأحدث أولاً، الأقدم، الأعلى قيمة، الأقل قيمة).
- ترقيم صفحات ذكي (Pagination).
