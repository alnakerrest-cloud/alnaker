## 1. جدول المهام الدورية والصيانة (Routine Maintenance Schedule)

لضمان أعلى درجات الاستقرار والاستجابة السريعة للنظام، يوصى باتباع جدول الصيانة الدوري التالي:

### أ. المهام اليومية (Daily Tasks)
- **مراجعة سجلات التشغيل (Vercel Runtime Logs):**
  - فحص وجود أي خطأ استثنائي (Unhandled 500 Errors أو React Server Digest Errors).
- **متابعة طلبات الواتساب:**
  - التحقق من صفحة `/admin/orders` للتأكد من سلاسة تسجيل الطلبات وتحديث حالاتها بواسطة طاقم المطعم.

### ب. المهام الأسبوعية (Weekly Tasks)
- **مراجعة سجل الرقابة والتدقيق (`/admin/audit`):**
  - فحص العمليات الإدارية الحساسة: تغييرات الأسعار، حذف الأطباق، وإضافة مستخدمين جدد.
- **مراقبة موارد قاعدة بيانات Neon:**
  - مراجعة استهلاك الـ Compute Hours وحجم البيانات المخزنة من لوحة تحكم Neon.
- **فحص اتصالات وسائط Cloudinary:**
  - التأكد من عدم تجاوز الحصة المجانية الشهرية لرفع ونقل الصور (Bandwidth & Storage).

### ج. المهام الشهرية (Monthly Tasks)
- **أخذ نسخة احتياطية أرشيفية خارجية:**
  - تنزيل تفريغ كامل لقاعدة البيانات عبر `pg_dump` وحفظه في مجلد مشفر غير متصل.
- **تنظيف الجلسات المنتهية (Session Garbage Collection):**
  - التأكد من إزالة الجلسات القديمة التي تجاوزت مهلة الـ 7 أيام من جدول `Session`.
- **مراجعة وتحديث أسعار ومواسم المنيو:**
  - تعديل ساعات عمل الفروع (توقيت صيفي / شتوي) والعروض الموسمية.

### د. المهام الربع سنوية (Quarterly Tasks)
- **تدوير المفاتيح الأمنية:**
  - تجديد `SESSION_SECRET` وتدوير كلمات المرور الإدارية للحسابات الرئيسية.
- **ترقية حزم ومكتبات المشروع:**
  - فحص الثغرات الأمنية عبر `npm audit` وتحديث الحزم الفرعية غير الكاسرة.

## 2. بروتوكول تسليم المشروع للمطور الجديد (Incoming Developer Handover Protocol)

إذا كنت مطوراً تستلم هذا المشروع للمرة الأولى، اتبع الخطوات التالية بالترتيب للبدء فوراً:

### الخطوة 1: استيعاب هيكل المشروع والمعمارية
1. اقرأ [README.md](./README.md) لفهم خريطة التوثيق.
2. اقرأ [01-project-overview.md](./01-project-overview.md) للتعرف على المكدس التقني وطبيعة العمل.
3. اقرأ [06-database-guide.md](./06-database-guide.md) لفهم الحاجز الصارم بين بيئة الإنتاج السحابية ووضع التطوير المحلي غير المتصل.

### الخطوة 2: إعداد جهاز التطوير
1. استنسخ المستودع الرئيسي:
   ```bash
   git clone https://github.com/EbrahimShoeib1999/naqer-menu.git
   cd naqer-menu
   ```
2. ثبّت الحزم بالأمر:
   ```bash
   npm install
   ```
3. انسخ ملف الإعدادات المحلي:
   ```bash
   cp .env.example .env.local
   ```
4. اترك `USE_BACKUP_DATA=true` لتعمل على وضع الـ Offline Mock ببيانات المنيو المعتمدة دون الحاجة للاتصال بقاعدة بيانات حية.
5. شغّل المشروع محلياً:
   ```bash
   npm run dev
   ```
6. افتح المنيو على [http://127.0.0.1:3000/ar](http://127.0.0.1:3000/ar) وتأكد من تصفح الأطباق والسلة.

### الخطوة 3: التحقق البرمجي قبل كتابة أي كود
تأكد من نجاح كافة الفحوصات المعتمدة:
```bash
npm run typecheck
node scripts/verify-persistence-guards.mjs
```

## 3. قائمة التحقق قبل وبعد النشر (Deployment Checklist)

### أ. فحص ما قبل النشر (Pre-Deployment Checklist):
- [ ] التأكد من اجتياز فحص الأنواع الصارم: `npm run typecheck`.
- [ ] التأكد من نجاح اختبار البناء المحلي: `npm run build`.
- [ ] التأكد من اجتياز اختبار حراس بيئة الإنتاج: `node scripts/verify-persistence-guards.mjs`.
- [ ] التأكد من عدم وجود أي سر أو كلمة مرور مكتوبة صراحة داخل الكود (`git diff`).
- [ ] التأكد من دفع التعديلات إلى فرع `main` على المستودعين (`origin` و `alnaker`).

### ب. فحص ما بعد النشر (Post-Deployment Smoke Test):
- [ ] فتح الرابط المباشر للإنتاج: `https://alnaker.vercel.app/ar`.
- [ ] التحقق من استجابة واجهة المنيو وسلاسة التمرير بين الأقسام.
- [ ] اختبار إضافة صنف إلى السلة ومراجعة الأسعار والإضافات.
- [ ] تجربة النقر على "إرسال الطلب عبر الواتساب" والتحقق من فتح الرابط الصحيح برقم الفرع.
- [ ] تسجيل الدخول للوحة التحكم الإدارية `/admin/login` والتأكد من فتح شاشة المؤشرات.
- [ ] فتح صفحة إضافة عرض جديد `/admin/offers/new` والتأكد من عدم حدوث أي خطأ في الـ Error Boundary.
- [ ] مراجعة Vercel Runtime Logs للتأكد من عدم وجود أي خطأ Digest أو تحذيرات معمارية.

## 4. القيود الفنية المعلومة والمسائل المعلقة (Known Limitations & Technical Debt)

استناداً إلى وثائق التدقيق وسجل التطوير التاريخي للمشروع:

1. **نظام البريد الإلكتروني (Email Notifications):**
   - *الوضع الراهن:* لا يوجد مزود بريد مفعل (راجع [05-email-system.md](./05-email-system.md)).
   - *الأثر:* استعادة كلمات المرور تتم يدوياً بواسطة المالك، والطلبات ترسل عبر الواتساب.
   - *المقترح:* دمج مزود Resend في التحديثات المستقبلية في حال طلبت الإدارة إرسال فواتير ضريبية بالبريد.
2. **بوابة إرسال الرسائل النصية القصيرة (SMS Gateway):**
   - *الوضع الراهن:* يعتمد التحقق من رقم الهاتف للعملاء على مزود `Pluggable OTP` تجريبي داخلي.
   - *الأثر:* مناسب حالياً وبلا تكلفة، لكنه يتطلب ربط بوابة رسائل SMS رسمية (مثل VictoryLink أو Twilio) عند الرغبة في إرسال رموز التحقق الحقيقية لهواتف الزبائن خارج المتصفح.
3. **الدفع الإلكتروني عبر البطاقات البنكية (Online Payment Gateway):**
   - *الوضع الراهن:* النظام مهيأ لخيار `CASH` (الدفع نقداً عند الاستلام) وخيار `CARD` (عبر نقاط البيع المحمولة POS عند التوصيل).
   - *المقترح:* ربط بوابة دفع مصرية معتمدة (مثل Paymob أو Fawry أو Geidea) في المرحلة القادمة.
4. **تطبيق الهاتف المستقل (Mobile Native App):**
   - *الوضع الراهن:* الموقع مبني كـ Progressive Web App (PWA) سريع التجاوب مع شاشات الهواتف ولا يحتاج للتنزيل من المتاجر.
